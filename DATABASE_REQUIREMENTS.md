# Database Design Requirements

**English** · [Português](DATABASE_REQUIREMENTS.pt.md)

This document defines the database design and data-formatting requirements for LabChem Registry. It is based on an analysis of the workbook [2026 Todos labs TEMA.xlsx](https://uapt33090-my.sharepoint.com/:x:/g/personal/lrocha_ua_pt/IQAWNeX4mo45S6fXA5kON1MQAeEI0trkb8UDvVU3lHDq-_Q?e=ttVMRJ), accessed on 21 September 2026, and on the project requirements.

## 1. Findings from the source workbook

The workbook contains ten sheets covering general reagents, gas cylinders, individual laboratories, storage cabinets, and items that could not be found. Its data must not be copied directly into a production table because:

- equivalent fields have different names, such as `Name`/`Nome`, `Supplier`, `Storage`, `Localização`, `Link to SDS`, and `Link to MSDS`;
- some sheets contain several independent tables and repeated headers;
- headings, legends, inventory dates, and operational notes appear among data rows;
- dates are stored as Excel numbers, formatted text, or `?`;
- quantities combine numbers, units, counts, and comments in one value;
- status, expiry information, purity, and comments are sometimes embedded in the reagent name;
- locations are free text and do not consistently separate laboratory, cabinet, and shelf;
- the same chemical may occur in several physical containers, but containers have no stable common identifier;
- CAS values contain leading spaces, missing values, and at least one value that appears to be another identifier;
- gas cylinders require attributes not consistently used for ordinary reagent containers.

The workbook is therefore a migration source, not the target database model.

## 2. General design principles

1. Use PostgreSQL as the primary database on the institution's internal network.
2. Store one database record for each physical container or gas cylinder.
3. Separate the chemical identity from the physical inventory unit.
4. Normalize laboratories, cabinets, and shelves instead of storing a complete location as free text.
5. Use internal immutable identifiers; do not use names, CAS numbers, or spreadsheet row numbers as primary keys.
6. Preserve the original imported values for traceability while storing normalized values separately.
7. Never hard-delete inventory or audit records through normal application workflows.
8. Use UTC timestamps in the database and render them in the user's local timezone.
9. Store controlled states and units as codes rather than translated display text.
10. Enforce access rules in the backend/API, not only in the user interface.

## 3. Required data model

### 3.1 Chemical

Represents a chemical identity shared by one or more inventory units.

| Field | Type | Requirement |
|---|---|---|
| `id` | UUID | Primary key, generated by the system |
| `preferred_name` | text | Required, trimmed |
| `formula` | text | Optional; preserve capitalization and chemical notation |
| `cas_number` | text | Optional; normalized to `N{2,7}-NN-N` and checksum-validated |
| `physical_state` | code | Optional: solid, liquid, gas, mixture, other, unknown |
| `notes` | text | Optional; must not replace structured fields |

A chemical may have alternative names in a separate `chemical_alias` table. A missing CAS number is allowed. CAS alone must not be treated as universally unique because mixtures and data-quality exceptions exist; suspected duplicates must be reviewed during import.

### 3.2 Inventory unit

Represents one physical container, package, or cylinder.

| Field | Type | Requirement |
|---|---|---|
| `id` | UUID | Primary key and future QR-code value |
| `chemical_id` | UUID | Required foreign key to `chemical` |
| `manufacturer_id` | UUID | Optional foreign key |
| `catalog_number` | text | Optional; stored as text |
| `lot_number` | text | Optional |
| `concentration_or_grade` | text | Optional |
| `nominal_quantity` | decimal | Optional; must be positive |
| `quantity_unit` | code | Required when nominal quantity is present |
| `container_count` | integer | Default 1; positive |
| `expiry_date` | date | Optional; no guessed day or month |
| `location_id` | UUID | Required while the unit is available |
| `responsible_user_id` | UUID | Optional foreign key |
| `status` | code | Required; default `available` |
| `label_photo_id` | UUID | Optional foreign key to stored media metadata |
| `notes` | text | Optional |
| `created_at`, `updated_at` | timestamp | Required, system-managed |

Allowed initial statuses are `available`, `retired`, `not_found`, and `pending_review`. Extra states require an explicit migration and documented business meaning.

Partial consumption and remaining quantity are outside the first-version scope. Spreadsheet values such as `Estimated quantity left` must be retained in migration source data or notes but must not drive current stock calculations.

### 3.3 Gas-cylinder extension

Gas-specific data belongs in a one-to-zero-or-one `gas_cylinder` record linked to an inventory unit:

- cylinder or supplier reference;
- gas mixture/composition, when the chemical record alone is insufficient;
- replacement-required flag;
- cylinder-specific notes.

A gas cylinder remains an inventory unit and follows the same status, location, and audit rules.

### 3.4 Location hierarchy

Locations must use explicit foreign keys:

```text
laboratory → cabinet/storage unit → shelf
```

- A laboratory has a unique institutional code, such as `3.2.22`, and a display name.
- A cabinet belongs to exactly one laboratory.
- A shelf belongs to exactly one cabinet.
- Codes must be unique within their parent location.
- A special staging location may be used for `pending_review` or `not_found` imports.
- Descriptions such as “vapour extraction cabinet” are storage-unit attributes, not reagent-name text.

Individual positions within a shelf are not required.

### 3.5 Manufacturers and safety documents

Manufacturers/suppliers must be normalized so spelling variants do not create duplicate entities. Original supplier text must still be retained during import.

Safety Data Sheets must be stored in a separate `safety_document` table with:

- internal identifier;
- chemical or inventory-unit association;
- source URL or managed file reference;
- language;
- revision/effective date, when known;
- document type (`SDS` or legacy `MSDS`);
- creation timestamp.

Do not store a hyperlink label without its actual URL or file reference.

### 3.6 Users and audit history

The data model must support `user`, `laboratory_manager`, and `administrator` roles. Every state-changing operation must create an append-only audit event containing:

- event identifier;
- inventory-unit identifier;
- user identifier, or a designated import/service identity;
- event type;
- timestamp;
- previous and new structured values, where applicable;
- optional reason or comment.

At minimum, audit addition, record edits, location changes, and retirement. Retirement changes the status; it does not delete the record.

### 3.7 Label recognition

OCR or AI output must first be stored as a draft linked to the image and recognition metadata. It must include the extracted values, confidence values when available, model/service version, and processing timestamp. A draft becomes production data only after a user confirms or corrects it.

## 4. Data formatting rules

- Save text as Unicode and trim leading/trailing and non-breaking spaces.
- Preserve accents and chemical formula capitalization.
- Store names without expiry dates, storage instructions, or status comments appended to them.
- Store CAS numbers as text, remove surrounding whitespace, validate format and checksum, and flag failures for review.
- Store dates as ISO dates (`YYYY-MM-DD`); keep unknown dates as `NULL`, never as `?`.
- If only a year or month is known, record the precision explicitly instead of inventing a complete date.
- Separate quantities into decimal value and controlled unit; do not save `2.5 L`, `10 g + 10 g`, or `30% | 50%` as calculated numeric values without review.
- Use decimal points internally regardless of UI locale.
- Store catalogue, lot, room, cabinet, shelf, and cylinder references as text to preserve leading zeros and letters.
- Use `NULL` for unknown values; empty strings, dashes, and question marks are not valid substitutes.
- Put operational comments in notes or audit events, not in identity fields.
- Treat uploaded photos and documents as managed objects; store metadata and references in the database rather than large binary values unless the storage architecture explicitly requires it.

## 5. Constraints and indexes

The database must enforce foreign keys and check constraints. At minimum, provide indexes for:

- normalized chemical name and aliases, including partial-text search;
- CAS number;
- manufacturer and catalogue number;
- inventory status;
- laboratory, cabinet, and shelf;
- expiry date;
- audit events by inventory unit and timestamp.

Potential duplicates should be detected using a combination of chemical, manufacturer, catalogue number, lot, location, and source-row information. Duplicate detection must warn or queue a review; it must not silently merge physical containers.

## 6. Spreadsheet migration requirements

1. Import every source sheet into a staging area before creating production records.
2. Record the source workbook, sheet, row, import batch, and original cell values.
3. Detect and exclude headings, legends, blank rows, and repeated headers from inventory records.
4. Map source column variants to the canonical schema.
5. Split embedded values only when the transformation is deterministic; otherwise queue them for review.
6. Normalize supplier names, locations, dates, units, and CAS values.
7. Treat “Não encontrei” rows as `not_found` candidates, not as available inventory.
8. Compare the April and August 2026 gas sheets as snapshots; do not blindly import both as independent cylinders.
9. Produce a migration report listing accepted rows, warnings, rejected rows, and suspected duplicates.
10. Require human approval before promoting staged records into production.

## 7. Minimum acceptance criteria

The database design is acceptable when:

- every physical unit has a stable unique identifier;
- every available unit resolves to a laboratory, cabinet/storage unit, and shelf;
- searches work by name, partial name, CAS, manufacturer, catalogue number, and laboratory;
- ordinary searches exclude retired units by default;
- location changes and retirement are fully auditable;
- invalid dates, CAS values, units, and unresolved locations cannot silently enter production;
- OCR results and spreadsheet imports require confirmation;
- the web interface and messaging bots use the same backend and database.

## 8. Out of scope for the first version

- partial-consumption tracking;
- real-time remaining-quantity calculations;
- numbered positions within a shelf;
- mandatory QR-code printing.

The schema must nevertheless support adding QR codes later without changing inventory-unit identifiers.
